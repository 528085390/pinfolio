# 和别的东西比

pinfolio 故意做得很小。这一页是「我要不要用它代替 X」的老实回答 —— 包括答案是「不要」的那些情况。

下面这些项目没有任何一个被贬低的意思：Memos、HomeBox、Uptime Kuma、linkding 在各自那一件事上都比 pinfolio 做得好，它们只是彼此不说话。

2026 年 10 月核对过一次。功能会变，拿不准就去看项目本身。

## pinfolio 不做的事

- **多用户。** 一个密码、一个主人，没有角色、没有邀请、没有分享。家里或团队要分账号的，上表里每一个项目都有真正的用户管理，pinfolio 没有。
- **SSO、OIDC、两步验证。** 只有 scrypt 密码、30 天滑动会话、可以踢下线的设备列表，以及给脚本用的 Bearer token。鉴权面就这么大。
- **探测你的服务。** 观测页是架在 Uptime Kuma 之上的界面，数据走 Kuma 的 socket.io API。没有 Kuma 就没有观测页。pinfolio 自己从不主动连你的服务。
- **写你的信箱。** 邮件是设计上只读的：只发 `SELECT` / `SEARCH` / `FETCH BODY.PEEK[]`，一行 `STORE` 都没有，所以点开一封信不会在服务器上标成已读。不能回信、不能移动、不能删除。
- **长期存指标。** 主机曲线只覆盖最近 24 小时；长期记录是 `data/audit/` 里每天一份的心跳 CSV。没有告警引擎，也不接 Prometheus / Grafana。
- **导入别家的数据。** 设置页的 JSON 导出是唯一的数据出口，没有 Memos / HomeBox 导入器，也不打算做。

## 什么时候该用别的

### Memos —— 只要便签，而且不止一个人用

Go、单文件、MIT。成熟、快、社区大，有多用户、分享、SSO。pinfolio 的便签页是「带标签的列表」，不是带评论、可见性和动态的时间线。只想记想法的话，Memos 更合适。

### HomeBox —— 台账就是全部需求

Go、一个容器、AGPL-3.0。标签、位置、附件、保修日期、CSV 进出、用户组。如果是给整个家做登记，HomeBox 在该深的地方更深：物品照片、数量、保额、购买信息、CSV 双向。pinfolio 只登记服务器 / 域名 / 账号加自定义字段，到此为止。

### Uptime Kuma —— 要的是告警，不是概览

Node、MIT。二十来种探测类型、几乎什么都能推送的通知、公开状态页、维护窗口、两步验证。pinfolio 完全没有通知引擎，它只是读 Kuma 然后画一个更安静的概览。没在跑 Kuma 的，从 Kuma 开始。

### linkding —— 书签

Python / Django、MIT。标签、全文搜索、按页面元信息自动打标签、浏览器扩展、REST API。pinfolio 里根本没有「书签」这个概念。

### 也值得看看

flatnotes、Blinko（便签），TriliumNext（树状笔记），Joplin（客户端 + 同步），Vikunja（任务）。它们都不碰 pinfolio 的资产和观测那半边。

## 什么时候 pinfolio 是对的

- 一个人的东西，放在一台机器上。没有角色、没有邀请、没有分享 —— 这是故意的，因为省掉的正是鉴权面的大部分。
- 你已经在跑 Uptime Kuma（或者愿意跑），并且希望观测视图就挨着关于这些机器的便签。
- 你希望「关于某台服务器的便签」和「那台服务器」在同一个标签下面。
- 你宁愿备份一个目录，也不想备份三个库。

## 一起用

- **pinfolio + Kuma** 是设计上的搭配。观测页要 `KUMA_URL`（默认 `http://127.0.0.1:3001`），只在做备份时才读 Kuma 的库。
- **pinfolio + Memos / HomeBox / linkding** 能共存，但彼此什么都不共享：没有导入器、没有同步、没有公共标签库。同时跑两个便签应用，通常比只留一个更糟。
- pinfolio 不导入任何东西，要迁进来只能重录或者写脚本打 HTTP API（[docs/api.zh.md](api.zh.md)）。
