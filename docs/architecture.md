## 工程与文档

工程与文档：
- `README.md`（英文）/ `README.zh.md`（中文）—— 面向使用者的入口页：定位、功能一行一条、快速开始、数据与备份、两级目录树、开发命令、四条 FAQ、技术栈与出处、文档索引。细节不写在这里。
- `docs/features.md` / `docs/features.zh.md` —— **各页完整行为**（便签 / 标签 / 资产 / 观测台 / 邮件 / 全局），从 README 拆出来的，改行为要同步这里。
- `docs/api.md` / `docs/api.zh.md` —— **完整 HTTP API 表** + curl 示例。截图不随仓库发布（页面里是本机真实数据），要图就本地跑 `tools/screenshots/`。
- `AGENTS.md` —— 本文件，面向后续开发者/agent 的约定、模块职责、已知坑。
- `SNAPSHOT.md` —— **自动生成的可读快照**：资产总表 + 每条资产详情（备注、自定义字段）+ 全部便签 + 标签/字段总览，头部带生成时间与「数据最后变更」。任何写操作（POST/PUT/PATCH/DELETE）后 1.5 秒内自动重写（`server/snapshot.ts` 的 `scheduleSnapshot()`，由 `server/index.ts` 的 `/api/*` 中间件触发），启动时也生成一次；手动 `pnpm snapshot`。**不要手改，会被覆盖。**渲染在 `server/snapshot/markdown.ts`（纯函数），取数与写盘在 `server/snapshot/{rows,write}.ts`；隔离实例（`PINBOARD_DATA` 指到别处）不写这个文件。
- `start.cmd` —— 启动器：先用 `/api/health` 探测，已在运行就只开浏览器；否则调 `run-pinboard.vbs` **后台隐藏启动**，轮询到 HTTP 200 后打开页面，窗口随即自己关掉（2026-10-20 用户要求不再前置控制台窗口）。
- `stop.cmd` —— 停止器：`tools\pinboard.ps1 stop`。后台隐藏运行后没有窗口可关，**停服务只能走它**。
- `run-pinboard.vbs` —— 隐藏窗口启动器（`sh.Run "cmd /c ... pnpm start >> logs\pinboard.log 2>&1", 0, True`），**必须 CRLF**。
- `tools/pinboard.ps1` —— `start|stop|restart|status|logs` 控制脚本（根目录按脚本位置推导）。**必须存成 UTF-8 带 BOM**（`logs` 用 `Get-Content -Encoding UTF8`，否则 PS 5.1 按 GBK 解码日志、中文乱码）。
- `logs/` —— 运行日志 `pinboard.log`（追加，不轮转；不进版本库）。
- `docs/adding-assets.md` —— **录入手册（加资产、加便签都读这一篇）**：资产字段表 / 枚举 / 自定义字段 / 四类模板 / 批量脚本，便签字段表 / 标签抽取规则 / 完成与归档语义 / 批量导入，两页各自独立，末尾一页速查。给后续会话直接照做。
- `docs/mail-page-requirements.md` —— **邮件页的唯一需求来源（v1.1 定稿）**：目标/非目标、FR-1…FR-29、NFR-1…NFR-10、数据模型、接口约定、12 条验收、Q1–Q10 定案、D1–D6 决策（D1 永不回写已读、D2 本地已读标记、D3 Gmail 实测暂缓、D4 远程图片默认显示 + 保留邮件样式、D5 60 秒轮询自动收信、D6 账号级 SOCKS5 代理）。动邮件页之前先读它——**别把「发信 / 删除 / 标已读」加回来**。
- `docs/pitfalls.md` —— **已知问题与坑的完整 35 条**（编号稳定，「见坑 N」都指这里）；`AGENTS.md` 只留最要命的 5 条。
- `docs/status-history.md` —— **2026-10-19 → 2026-10-21 的 23 条进展记录**（每条含当时的测试断言条数与真机复测结论）。`AGENTS.md` 的「状态」只留当前状态，**新增进展往这里写**。

- `docs/deploy.md` —— **部署的唯一手册**（2026-10-26 加）：Docker Compose（含 Caddy profile）、裸机 Linux/macOS（systemd 示例）、Windows、环境变量表、升级与回滚、观测页要不要接 Kuma、验收清单。改部署方式要同步这里。

- `data/` —— 运行时 SQLite 数据（不进版本库）；`data/backups/` 是自动备份包，`data/audit/` 是长期心跳归档（都不进版本库）。
- `dist/web/` —— 前端构建产物，server 直接托管（不进版本库）。
- `tests/` —— 冒烟 / 端到端 / 单测（`tests/unit/`，`pnpm test:unit`，node:test 秒级）+ 串行 runner（`tests/run.mjs`）+ 假 IMAP（`tests/fakeimap/`）。
- `tools/screenshots/` —— 截图脚本（产物写 `tmp/`，已被 .gitignore 忽略）。
- `tools/chrome-path.mjs` —— e2e 与截图脚本共用的浏览器路径解析：`CHROME_PATH` → Playwright 自带 chromium → 系统 Chrome。**公开仓库里别把家目录写死进脚本**（既泄漏路径又让别人的机器跑不起来），2026-10-21 起所有脚本都改成 `import { CHROME as exe }`。
- `tools/node-metrics/` —— **6 台服务器的采集端**（2026-10-22 加，安装/排错/回滚见该目录 `README.md`）：`node-metrics.sh`（110 行，只读 `/proc` + `df` + `systemctl`，零依赖、零常驻，跑完即退）、`install.sh`（写 `/etc/node-metrics.conf` 600 + 装 unit/timer + 立刻跑一次）、`node-metrics.service` / `.timer`、`nginx-metrics.conf`（my-server 上那两段 location，PUT 落盘 + GET 读回）、`build-install.mjs`（把上面四件内联成**单文件安装器** `node-metrics-install.sh`，`--check` 逐字节校验 heredoc + 指纹，别手改生成物）。单文件安装器托管在 my-server 的 nginx `/nm/`（`alias /var/www/nm/`、`Cache-Control: no-store`、**不带 token**），主机页那条安装命令就是 `curl` 它 + `sudo bash`；改完采集端记得 `node tools/node-metrics/build-install.mjs` 重新生成并重传（`bash -n` 过一遍）。**改采集字段要同步三处**：这里、`server/metrics/*` 的取用、`web/pages/hosts/HostCard.tsx` 的展示。
- `host-services.json` —— **主机页服务 chip → 观测项的映射**（2026-10-22 加；仓库只带 host-services.example.json，本机那份不进版本库）：`[{ host, unit, match?, monitor? }]`，`host` 是采集端的 `HOST_ID`、`unit` 是采集端 `WATCH_UNITS` 里的服务名，`match` 在该主机分组内按观测项短名做不区分大小写的包含匹配（`monitor` 可直接钉 id）。改完不用重启（每次 `GET /api/hosts` 重新解析），对不上就退回纯文字 chip。
- `quick-links.json` —— **观测台顶部「快捷入口」卡的数据**（2026-10-22 加）：`[{ name, url, note?, label?, icon? }]`，纯数据、**不进版本库**（仓库里只带 `quick-links.example.json`，同 `monitor-links.json` 的规矩）。服务端 `server/kuma/quick.ts` 每次请求热读（改完刷新页面即生效，不用重启），并进 `/api/monitors` 的 `quick` 字段。**这些卡不产生 Kuma 检查**——想加个入口别去建观测项，往这个文件里加一条就行。
- `tmp/` —— 运行期临时产物（日志、截图），可整目录删除（见「可清理项」）。

服务端（Node 24 + Hono + `node:sqlite`，无原生编译）：
- `server/schema/core.ts` / `server/schema/mail.ts` / `server/schema/metrics.ts` —— 建表语句（core：tags / field_defs / assets / notes / note_tags / asset_tags + 5 个索引；mail：mail_accounts / mail_local_read；metrics：host_metrics + 1 个索引，见下面「主机指标」三条）。`server/db.ts` 只负责打开库、封装 `all/get/run` 与标签同步（`syncNoteTags`/`setAssetTags`），启动时调 `migrate(db)`。
- `server/migrations.ts` —— **表结构演进的唯一入口**：`MIGRATIONS = [{ version, up(db) }]` + `PRAGMA user_version`，每步一个事务、失败回滚；v1 = 建表 + 老库补列（`notes.done` / `mail_accounts.proxy`）+ 预设标签，v2 = settings / sessions / api_tokens。**只追加，不改旧步**；老库靠列存在性探测归一。`migrate(db, MIGRATIONS, { dataDir })` 在动库之前会调 `server/backup/premigrate.ts` 拍一张快照（全新库跳过），拍不出来直接抛错中止升级；`registerPreMigrate(fn)` 另留了钩子口。
- `server/secrets/crypto.ts` / `key.ts` / `migrate.ts` —— **静态加密**：`HKDF-SHA256(secret, info="pinfolio/v1")` 派生 AES-256-GCM key，存储格式 `enc:v1:<iv>:<tag>:<ct>`；主密钥 = `PINBOARD_SECRET` → `data/secret.key` → 首次启动生成（0600）；`migrateSecrets()` 每次启动把还躺在明文里的 `mail_accounts.password`、`data/kuma-pass.txt`、`data/metrics.json` 的 `base` 就地加密（幂等）。**只防备份/库文件泄漏，防不了进程被控。**
- `server/backup/{core,tar,collect,local,remote,run,schedule}.ts` —— **自动备份**（2026-10-26 加，设计见 `docs/superpowers/specs/2026-10-23-pinfolio-oss/05-backup.md`）：`core.ts` 是纯函数（文件名 `pinfolio-YYYYMMDD-HHMM.tar.gz`、周日才带 `kuma.db`、保留 N 份时排除 `pre-migrate-*`、CSV 转义与表头）；`tar.ts` 手写 ustar（只用 gzip + 自家 512 字节头，**不引依赖**）；`collect.ts` 取库快照（模块级 `backup()`，不是 `DatabaseSync.prototype.backup`）+ 当天心跳 CSV + 观测项 JSON；`local.ts` 打包落 `data/backups/`；`remote.ts` 写 MySQL / PostgreSQL（`mysql2` / `pg` **懒加载**，没配远端就不 import）；`run.ts` 编排两个目的地 + 上传后回读 sha256 校验；`schedule.ts` 进程内定时器（默认 03:00，`BACKUP=0` / `off` / `false` 关）。`premigrate.ts` 是**迁移前快照**（`VACUUM INTO` 拍 `data/backups/pre-migrate-v<旧版本>-<时间戳>.db`，保留 5 份；全新库不拍；拍不出来就不升级）——由 `server/migrations.ts` 的 `migrate(db, MIGRATIONS, { dataDir })` 调用，`server/db.ts` 传 `DATA_DIR`。**心跳按 UTC 日边界查**（Kuma 的 `heartbeat.time` 存 UTC，见坑 41）；远端表的 `id` 是 `randomUUID()`、`created_at` 是 `VARCHAR(32)` 存 ISO 串（见坑 42、43）。

- `server/tags.ts` / `server/dates.ts` —— 纯函数（不碰库、不碰网络）：`extractTags`（TAG_RE 支持中英文标点前缀）、`tagColor`/`TAG_COLORS`/`PRESET_TAGS`；`daysLeft()` 到期天数。**纯逻辑放这里才测得了**（`db.ts` 一 import 就打开 SQLite），db.ts / meta.ts 再导出。
- `server/hydrate.ts` —— `hydrateNotes`/`hydrateAssets`：批量 IN 查询拼 tags、asset、noteCount，解析 custom JSON。
- `server/routes/notes.ts` —— 便签 CRUD + 筛选（q/tag/pinned/archived/assetId），内容变更时同步标签。
- `server/routes/assets.ts` —— 资产 CRUD + 筛选（q/kind/status/tag），GET /:id 附带 `linkedNotes`（已 hydrate 标签）。
- `server/routes/tags.ts` —— 标签 CRUD，GET 带 notes/assets 计数。
- `server/routes/fields.ts` —— 自定义字段定义 CRUD（key 正则 `^[a-zA-Z][a-zA-Z0-9_]*$`，type 限 text/number/date/url/select/bool）。
- `server/kuma/routes.ts` —— 观测台的 HTTP 面（只做取数、拼响应、写回）：列表走 `feed.ts` 的 `collectCached()`（失败时用 `lastPayload()` 回旧值并标 `stale`），详情把脱敏后的 monitor + 最近 24h 心跳 + 立即观测配方 + 跳转链接拼一起（`monitor-links.json` **按 `id` 匹配，`name` 只兜底**——名字能在抽屉里改）。**校验与归一化不在这个文件里**：PATCH 的规则在 `server/kuma/patch.ts`（纯函数、有单测），HTTP 小工具在 `server/kuma/http.ts`。
  写接口都在这里：`GET /:id`（详情：脱敏后的 monitor + 最近 24h 心跳 + 立即观测配方 + 跳转链接）、`PATCH /:id`（改名/介绍/频率/超时重试，校验后整体回传 Kuma）、`POST /:id/pause|resume`、`DELETE /:id?confirm=<名字>`（先备份 Kuma 库再删）、`POST /:id/check`（跑立即观测配方）。**所有写接口都要求 `Content-Type: application/json`**（挡跨站表单提交，DELETE 只在带 body 时校验）；写完统一 `invalidate()` 清缓存 + 15 秒内强制绕过 Kuma 的状态页缓存 + 防抖 1.5 秒后 spawn `kuma/tools/snapshot.cjs` 重生成 `kuma/SNAPSHOT.md`。
- `server/kuma/client.ts` —— 跟 Kuma 说话的 **socket.io 客户端**（不是 HTTP）：`connect()` 登录后常驻连接（`reconnection:false`，**别加 `transports:['websocket']`**，会握手超时）、`call()` 等 ack（20 秒超时，`res.ok===false` 抛 `KumaError`）、`listMonitors()`（先 `on('monitorList')` 再 `emit('getMonitorList')`，ack 里没有数据）、`getMonitor`/`getBeats`/`editMonitor`/`pauseMonitor`/`resumeMonitor`/`deleteMonitor`/`kickCheck`。`toView()` 只输出白名单字段，`redactUrl()`/`describeTarget()` 把 URL 里的账号密码与 `key|token|pass|secret|auth|sign` 参数打码，**别把 Kuma 的原始 bean 直接吐给前端**（含 SSH 私钥）。脱敏与展示映射实际在 `server/kuma/redact.ts`（纯函数，可单测），client.ts 只再导出。
- `server/kuma/kuma-cli.ts` —— 建/删观测项走 **kuma 仓库的 CLI**（`../kuma/tools/kuma-monitor.cjs`，可用 `KUMA_CLI` 覆盖）：Kuma 前端已删，直接改库又绕不过它调度器的内存，所以 `add` / `del` / `group-add` / `group-del` 都 spawn 子进程（`windowsHide`、默认 60 秒超时、非 0 退出把 stderr 当错误文案抛上去）。`runKuma()` 回 stdout，`firstId()` 从「已创建监视器 id=130（…）」里抠 id；`ensureGroup(name)`（同名幂等）、`addMonitor(payload, groupId)`（payload 写临时文件再 `add <file> --group <id>`）、`deleteMonitor(id)`、`deleteGroup(id)`（**组里还有观测项时 CLI 会拒绝**，所以只能放在删完观测项之后）。
- `server/kuma/provision.ts` —— 「添加主机」顺带建观测项的**纯函数**（`tests/unit/kuma-provision.test.mts`）：`groupNameFor(host)`（有显示名用显示名，否则退回 id）、`planMonitors({hostId, address, groupName, port?, http?, services?})` 按固定顺序摊成 `{name, payload, unit?}`（端口 → HTTP → 服务；名字统一 `<组短名> / <服务名>`，`shortGroup()` 会剥掉括号段，所以观测页的 `shortName()` 照样能剥前缀；端口 1–65535、HTTP 必须以 `http(s)://` 开头、SSH 探测要 `ssh_command: 'systemctl is-active <unit>'`）、`mergeServiceRules(existing, additions)`（同 host+unit **覆盖** monitor id 而不是追加，否则 `resolveUnitMonitors` 会一直命中旧的）。
- `server/kuma/recipe.ts` —— **纯函数**（2026-10-21 拆出）：「立即观测」配方的解析与挑选。`parseRules()`（顶层数组与 `{recipes:[…]}` 两种写法都认，写坏了当没配方）、`normalizeSteps()`（补默认 label，没有字符串 `type` 的项丢掉，`hint` 只认字符串）、`resolveFromRules()`（**先按 `id` 再按 `name`** 匹配，改名不会悄悄换掉动作；置灰原因三档：配方自带的 `disabledReason` → 不认识的步骤类型 → 没有步骤；没配方时非推送型默认 `[{type:'kuma-check'}]`、推送型置灰——要外部心跳驱动，没法本地触发）、`timeoutOf()`（按类型取默认 25/15/30 秒，配方里的 `timeout` 覆盖，夹在 1 秒与剩余预算之间）、`clip()`/`statusText()`。单测在 `tests/unit/kuma-recipe.test.mts`。
- `server/kuma/runner.ts` —— 配方执行器（2026-10-21 拆出）：步骤类型 `kuma-check`（重启检查循环，Kuma 几百毫秒内真探一次）/ `http`（发请求，优先读回包里的 `message|msg|error`）/ `command`（`shell:false` + argv 数组，不过 shell）。执行语义：顺序跑、失败即中止、整体 60 秒上限、每步独立超时，逐步骤回 `{type,label,ok,detail,ms}`。
- `server/kuma/actions.ts` —— 只剩「读配置 + 挑配方」的门面：`ACTIONS_FILE`（`process.env.MONITOR_ACTIONS` 可覆盖路径）**每次请求热读**根目录的 `monitor-actions.json`（改完不用重启），解析失败当没配方；`resolveAction(m)` = `resolveFromRules(loadRules(), m)`。`runRecipe` 与类型从这里再导出，所以 `routes.ts` 的 import 零改动。
- `server/mail/types.ts` —— 邮件数据模型：`MailRow`（列表行）、`MailMessage`（正文）、`MailAttachment`、`FolderInfo`、`ListResult`。
